# `deck_category` 配置逻辑分析

> 范围：仅对该 YAML 配置片段做位运算/正确性/与现有映射对比的**纯分析**，不修改任何代码库文件。

## 一、配置原文

```yaml
- id: deck_category
  name: 卡组归属
  description: "卡片所属卡组段:融合/同调/超量/连接为额外卡组,空字符串为主卡组"
  items:
    - condition: (d.type & 64) > 0
      value: 融合
    - condition: (d.type & 8192) > 0
      value: 同调
    - condition: (d.type & 8388608) > 0
      value: 超量
    - condition: (d.type & 67108864) > 0
      value: 连接
    - condition: (d.type & 64) = 0 AND (d.type & 8192) = 0 AND (d.type & 8388608) = 0 AND (d.type & 67108864) = 0
      value: ''
```

## 二、它做了什么

`d.type` 是 YGOPRO `cards.cdb` 数据库 `datas` 表里的**位掩码字段**，每一位代表一种卡片类型标记。该配置把每张卡分到一个"卡组归属"：

- **额外卡组**：融合 / 同调 / 超量 / 连接 怪兽
- **主卡组**：以上四种都不是的卡（魔法、陷阱、通常/效果/仪式/灵摆怪兽等），`value` 为空字符串 `''`

位值与 YGOPRO 常量对照：

| 位 | 十进制 | 十六进制 | 常量 | 归属 |
|----|--------|----------|------|------|
| 6  | 64       | 0x40      | TYPE_FUSION  | 额外（融合） |
| 13 | 8192     | 0x2000    | TYPE_SYNCHRO | 额外（同调） |
| 23 | 8388608  | 0x800000  | TYPE_XYZ     | 额外（超量） |
| 26 | 67108864| 0x4000000 | TYPE_LINK    | 额外（连接） |

位值**全部正确**，与 YGOPRO 官方 `TYPE_*` 常量一一对应。

## 三、与 YGOPRO 规则的契合度

| 卡片类型 | 是否进额外卡组 | 本配置归类 | 结论 |
|----------|----------------|------------|------|
| 融合怪兽 | 是 | 融合 | ✅ |
| 同调怪兽 | 是 | 同调 | ✅ |
| 超量怪兽 | 是 | 超量 | ✅ |
| 连接怪兽 | 是 | 连接 | ✅ |
| 仪式怪兽 | **否**（仪式怪兽在主卡组） | 主卡组（`''`） | ✅ 正确未把 bit128 算入额外 |
| 灵摆怪兽（非额外） | 否（组卡时在主卡组） | 主卡组（`''`） | ✅ 组卡用途正确 |
| 灵摆+超量/连接等 | 是 | 命中首个匹配的额外项 | ✅ |
| 通常/效果/魔法/陷阱 | 否 | 主卡组（`''`） | ✅ |

> 注：灵摆怪兽从场上被破坏时进额外卡组是**对局中的状态**，不影响**组卡时的卡组归属**判定，所以这里归主卡组是对的。

## 四、"互斥"语义与 items 求值方式

描述声称"主/额外，互斥"。互斥在 YGOPRO 数据里**事实上成立**——一张卡的 `type` 不会同时带融合+同调+超量+连接中的两个位（不存在"融合同调"这种单帧卡片）。

因此无论 SDK 的 `items` 求值是哪种语义，结果都正确：

- **首匹配优先（first-match wins）**：按顺序命中第一个，最后一条做兜底，互斥成立。✅
- **全匹配多标签（all-match）**：主卡组卡只会命中最后一条 `value: ''`；额外卡组卡只会命中其对应那一条。由于事实互斥，也不会出现多命中。✅

但要注意：描述里写"互斥"是一种**约定层面的声明**，真正决定行为的是 SDK。如果将来 SDK 改成支持多标签叠加（像现有 `monster_type` 那样标注"可叠加"），这套配置依然正确，因为它依赖的是位本身的互斥性，而非 SDK 语义。

## 五、与现有 `monster_type` 映射的对比

代码库 [labels.yaml](file:///workspace/labels.yaml#L74-L87) 已有 `monster_type`：

```yaml
  # 怪兽分类（可叠加）
  - id: monster_type
    name: 怪兽分类
    items:
      - condition: (d.type & 64) > 0
        value: 融合
      - condition: (d.type & 8192) > 0
        value: 同调
      - condition: (d.type & 8388608) > 0
        value: 超量
      - condition: (d.type & 67108864) > 0
        value: 连接
      - condition: (d.type & 128) > 0
        value: 仪式
```

| 维度 | `monster_type`（现有） | `deck_category`（待分析） |
|------|------------------------|--------------------------|
| 回答的问题 | 这是什么类型的怪兽？ | 这张卡组卡时放哪个卡组？ |
| 叠加性 | 可叠加 | 互斥 |
| 包含 bit128 仪式 | ✅ 含 | ❌ 不含（仪式属主卡组，正确） |
| 兜底项 | 无（非怪兽可能都不命中） | 有（主卡组 `value: ''`） |
| 位值 | 十进制 | 十进制（风格一致 ✅） |

两者**不冲突**：用相同 4 个位回答不同问题，是合理的并列映射。`deck_category` 把仪式排除在额外之外、并补上主卡组兜底，是它相对 `monster_type` 的关键增量。

## 六、可改进点（仅作分析指出，不改文件）

1. **空字符串 `value: ''` 不一致**：现有配置（如 [card_type](file:///workspace/labels.yaml#L33-L44)、[spell_type](file:///workspace/labels.yaml#L47-L61) 的 `value: 通常` 兜底）都用**具名标签**做默认值，没有用空字符串。`''` 作为筛选值不好用（用户怎么过滤"主卡组"卡？）。建议改 `value: 主卡组`。

2. **末尾兜底项在首匹配语义下冗余**：若 SDK 是首匹配，前四条都没命中 ⇒ 四个位必为 0 ⇒ 末条必然成立。但写出来**显式且安全**，可读性好，可保留。

3. **"互斥"措辞依赖 SDK 语义**：描述应与 SDK 实际 `items` 求值方式对齐。若 SDK 是全匹配多标签，建议描述里改成"事实上互斥"以免误导。

4. **位值风格**：与 `labels.yaml` 内 `monster_type` 一致（十进制），与 `extensions/effect-type.yaml`、`extensions/series.yaml`（十六进制 `0x40` 等）不一致。放在 `labels.yaml` 里则保持现风格即可，无需改。

## 七、结论

- **逻辑正确**：四个位值匹配 YGOPRO 常量；融合/同调/超量/连接 → 额外，其余 → 主，符合规则；仪式被正确归入主卡组。
- **与现有映射不冲突**：和 `monster_type` 回答不同问题，可并列存在。
- **主要可改进点**：把主卡组的 `value: ''` 换成 `value: 主卡组`，以与全配置风格统一、提升可筛选性。
